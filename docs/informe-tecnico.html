2. Cómo está organizado el código

Monorepo, no diez repositorios. Es lo que recomienda ExplicacionTec.md para un equipo de tres personas: un solo sitio donde buscar, un solo CI que configurar bien, y los cambios que cruzan servicios caben en un commit.

hub-negocios/
├── packages/SharedKernel/     infraestructura común a los 10 servicios
├── services/                  un microservicio por carpeta
├── tests/                     un proyecto de pruebas por servicio
├── docker/                    arranque de Postgres (bases y roles)
├── docs/                      arquitectura, diagramas y pendientes
└── docker-compose.yml         entorno local completo

Cada servicio sigue arquitectura hexagonal en tres capas:

CapaQué contieneDe qué depende
Domain/Entidades, objetos de valor y puertos (interfaces)De nada. Ni EF Core ni ASP.NET
Application/Casos de usoSolo del dominio
Infrastructure/EF Core, controladores, clientes HTTPDe todo lo anterior

Que el dominio no dependa de nada tiene una consecuencia muy concreta y muy práctica: los tests de lógica de negocio corren sin base de datos y sin Docker, en milisegundos. Por eso los dobles de prueba están escritos a mano en vez de con una librería de simulación: si hiciera falta simular un DbContext para probar una regla de negocio, querría decir que la regla se ensució con infraestructura.

Por qué hay un núcleo compartido

La propia especificación pedía comparar los Program.cs de varios servicios y desconfiar si divergían. Un paquete compartido convierte esa revisión manual en algo que no puede fallar: no divergen porque es literalmente el mismo código. El arranque de un servicio queda así:

builder.AddHubDefaults("order-service");      // logs, JWT, límites, health
builder.AddHubPersistence<OrderDbContext>();  // EF, interceptores, outbox

// ... solo lo propio de este servicio ...

app.UseHubDefaults();                          // middleware en el orden correcto
Regla para no romper esto

En el núcleo compartido vive infraestructura transversal, nunca lógica de negocio. Un núcleo que empieza a saber de órdenes o de reservas es el primer paso para volver a tener un monolito, solo que repartido en diez procesos y con la latencia de red de propina.

El patrón Outbox, y por qué no es opcional

Un caso de uso tiene que hacer dos cosas: guardar el cambio y avisar al resto del sistema. No hay forma de hacer esas dos cosas atómicamente contra dos sistemas distintos. Si el proceso muere en medio, o se confirmó la venta y nadie se enteró, o se avisó de una venta que no existe.

La solución es escribir el evento como una fila más de la misma transacción:

El publicador usa SELECT ... FOR UPDATE SKIP LOCKED, que es lo que permite que varias instancias del servicio publiquen a la vez sin pisarse: cada una se lleva las filas que bloquea y las demás pasan de largo en vez de esperar turno.

Hoy el publicador escribe en el log en vez de en un bus real (LoggingEventBusPublisher). Es deliberado, para poder desarrollar sin levantar RabbitMQ. Conectarlo de verdad es escribir una implementación de IEventBusPublisher y cambiar una línea.

Llamadas síncronas: tres defensas, tres problemas distintos

Cuando órdenes llama al catálogo, esa llamada lleva tres protecciones que suelen confundirse entre sí:

DefensaValorQué problema resuelve
Tiempo máximo de espera3 sQue una petición nuestra no se quede colgada esperando a quien no va a contestar. Sin esto los hilos se acumulan y caemos nosotros por culpa de otro.
Reintentos con espera creciente3 · 1s/2s/4sEl fallo pasajero: un despliegue en marcha, un pico de red. La espera crece porque reintentar de inmediato contra un servicio saturado es echar gasolina al fuego.
Cortacircuitos5 fallos / 30 sEl fallo sostenido. Deja de intentarlo y responde al instante. Protege a los dos: al otro, que deja de recibir tráfico mientras se recupera, y a nosotros, que dejamos de gastar 3 s por petición en algo que ya sabemos que falla.
Por qué las tres juntas

Sin el cortacircuitos, los reintentos empeoran una caída: multiplican por tres la carga justo cuando el otro servicio menos la aguanta. Es un error muy común y muy caro.

4. Convenciones de código

ReglaMotivo
Tablas en snake_case, mapeadas explícitamenteConvención de Postgres; evita tener que citar identificadores
Enums guardados como texto, no como númeroUn 2 en una columna no dice nada a las tres de la mañana. Y reordenar el enum en C# reinterpretaría en silencio todas las filas ya guardadas
Dinero en decimal / numeric(18,2)En coma flotante binaria 0,1 no es 0,1: los céntimos dejan de cuadrar
Fechas siempre en UTCUn sistema multi-tenant acaba sirviendo a varios husos
DTOs en los endpoints, nunca entidades de dominioSi el endpoint aceptara la entidad, el cliente podría mandar "status": "Paid" en el JSON y el enlazador lo asignaría sin preguntar
Los avisos del compilador son erroresEn diez servicios, un aviso que nadie mira se multiplica por diez y deja de verse
Versiones de paquetes centralizadasSi cada servicio fija las suyas, dos acaban corriendo EF Core distintos y el mismo código se comporta distinto

Formato de error único

Todos los servicios devuelven la misma forma, para que el frontend no aprenda diez maneras de saber que algo falló:

{
  "error": {
    "code": "ORDER_ITEM_UNAVAILABLE",
    "message": "Ya no están disponibles: Botella premium",
    "details": {},
    "trace_id": "0af7651916cd43dd8448eb211c80319c"
  }
}

El code es contrato estable y el message es para personas: mezclarlos obliga al frontend a comparar cadenas en español, que es lo que se rompe el día que alguien corrige una tilde. El trace_id viaja entre servicios en la cabecera X-Correlation-Id y se devuelve siempre, también en los errores: es el número que un cliente puede leernos por teléfono.

5. Base de datos

Una base por servicio

Diez bases sobre un mismo servidor físico, para ahorrar coste al principio sin renunciar al aislamiento lógico:

tenant_db   identity_db   catalog_db   order_db      billing_db
reservations_db   inventory_db   checkout_db   landing_db   notification_db
Regla que no se puede romper

Ningún servicio consulta la base de otro. Si órdenes necesita datos del catálogo, los pide por API o los recibe por evento. Un JOIN entre bases de dos servicios no se puede deshacer después sin reescribir medio sistema, porque para cuando duele ya hay veinte consultas que dependen de él.

Por eso cada línea de una orden guarda una foto del producto —nombre, precio, atributos— y no una referencia. Es duplicación a propósito: si mañana el negocio sube el precio, la factura de ayer tiene que seguir diciendo lo que el cliente pagó ayer. Leer el precio en vivo reescribiría el histórico de ventas, que además de incorrecto es ilegal en la mayoría de sitios.

Dos roles de Postgres, y esto es lo más importante de la sección

RolQuién lo usaPor qué
hubMigraciones y publicador de outboxEs dueño de las tablas. Necesita leer eventos de todos los clientes a la vez
hub_appEl servicio, al atender peticionesNo es dueño de nada, así que el aislamiento por fila sí se le aplica
Si esto se configura mal, el aislamiento no existe

En PostgreSQL, el dueño de una tabla se salta las políticas de Row-Level Security por defecto. Si el servicio se conectara con el usuario dueño, las políticas estarían escritas pero no se aplicarían nunca: parecería que hay aislamiento y no lo habría, sin que nada lo avisara. Verificar qué usuario hay en la cadena de conexión de producción es la comprobación número uno.

Índices que conviene conocer

  • Parcial sobre la outbox — solo indexa lo pendiente (WHERE published = false). La tabla se llena de eventos ya publicados que nunca se releen: indexarlos todos sería pagar por mantener un índice enorme del que siempre se usa la misma esquina.
  • Únicos por tenant, no globales — el número de orden, el slug, el correo del usuario. Dos negocios pueden tener cada uno su ORD-2026-000001, y el mismo correo puede ser cliente de dos negocios distintos.
  • Único con filtro — el dominio propio del tenant es único cuando existe (WHERE custom_domain IS NOT NULL). Sin el filtro, el segundo cliente sin dominio chocaría con el primero.

Migraciones

Una migración inicial por servicio, generada con EF Core y editada a mano para añadir lo que EF no sabe expresar: las políticas de seguridad por fila y las restricciones CHECK. Cada servicio gestiona solo las suyas; ninguna migración toca la base de otro.

6. Concurrencia: el problema de vender dos veces lo mismo

Es el punto más delicado del sistema y el que más caro sale si se hace mal. Dos clientes reservan la última mesa en el mismo instante:

Cliente A                          Cliente B
─────────                          ─────────
lee cupo → queda 1
                                   lee cupo → queda 1
escribe cupo = 0  ✓
                                   escribe cupo = 0  ✓

Resultado: dos reservas confirmadas para una sola mesa.

Un if (cupo > 0) en el código no lo evita, por muy bien escrito que esté: entre leer y escribir cabe otra transacción. La solución está en la base de datos, no en la aplicación:

SELECT * FROM time_slots
WHERE id = $1 AND tenant_id = $2
FOR UPDATE                          -- ← bloquea la fila hasta el COMMIT

Con FOR UPDATE, B se queda esperando en la lectura hasta que A termina, y cuando por fin lee, ve el cupo ya en cero. Va en SQL a mano porque EF Core no tiene forma de expresar un bloqueo de fila, y los valores van siempre como parámetros, nunca concatenados.

Defensa en profundidad

Además del bloqueo hay una restricción CHECK que impide que el cupo baje de cero por ningún camino. El bloqueo es la defensa; el CHECK es la red por si algún día alguien escribe por otra vía.

El mismo patrón hará falta en inventory-service cuando se implemente. Está documentado en docs/pendiente.md.

7. Aislamiento entre clientes

Es la propiedad de seguridad más importante de un SaaS multi-tenant: que el negocio A no pueda ver jamás datos del negocio B. No se confía a una sola medida.

Tres fallos sutiles que se evitaron

Los tres están comentados en el código, porque son el tipo de cosa que alguien «simplifica» sin saber lo que está quitando.

El filtro no puede apuntar al contexto de base de datos

El patrón que sale en casi todos los tutoriales guarda el cliente en un campo del contexto y compara contra él. El problema es que EF Core cachea el modelo por tipo de contexto: la segunda petición reutiliza un modelo que sigue apuntando al contexto de la primera, y acaba filtrando por el cliente equivocado. Aquí se compara contra un valor estático, sin capturar instancia alguna.

Hay que limpiar el identificador al soltar la conexión

Las conexiones salen de un pool y se reutilizan. Si al no haber cliente no se limpiara el valor, una petición anónima heredaría el cliente de la anterior que usó esa misma conexión física. La política está escrita para que, sin valor, no devuelva ninguna fila: el estado por defecto es negar, no mostrar todo.

La outbox queda deliberadamente fuera del filtro

La lee un proceso de fondo que publica eventos de todos los clientes y que, por definición, corre sin cliente en contexto. Con filtro no vería una sola fila y ningún evento saldría nunca. Es una excepción consciente y está documentada donde toca.

8. Credenciales y superficie expuesta

Contraseñas

BCrypt con factor de coste 12. El factor no es decorativo: cada unidad duplica el trabajo. Doce deja cada comprobación en unos cientos de milisegundos —imperceptible al entrar, carísimo para quien pruebe millones de contraseñas contra una tabla robada—. Subirlo cuando las máquinas mejoren es lo que mantiene esto cierto dentro de cinco años.

Ataque por tiempo, y cómo se cerró

El login devuelve el mismo error tanto si el correo no existe como si la contraseña es incorrecta. Eso es lo habitual y no basta: si cuando el correo no existe la respuesta llega en un milisegundo y cuando sí existe tarda doscientos, cualquiera puede averiguar qué direcciones están dadas de alta cronometrando las respuestas. El mensaje es idéntico, pero el reloj lo cuenta todo.

Cuando el usuario no existe se comprueba igualmente contra un hash de descarte con el mismo factor de coste, para gastar el mismo tiempo. Hay un test que lo mide y falla si alguien elimina esa rama por parecerle código muerto.

Tokens

Token de accesoToken de renovación
Duración15 minutos14 días
Dónde vaCuerpo de la respuestaCookie HttpOnly, Secure, SameSite=Strict
Qué se guardaNadaSolo el hash, nunca el token
¿Revocable?No, hasta que caducaSí. Se rota en cada uso

El token de acceso lleva firmados el usuario, el cliente y el rol, y los demás servicios lo validan sin preguntarle a nadie. Eso es lo que permite escalar sin que identidad sea el cuello de botella, y es también la razón de que no se pueda revocar antes de tiempo: quince minutos es el equilibrio entre no molestar al usuario y que un token robado sirva de poco.

Del token de renovación solo se guarda el hash. Si se filtrara la tabla —una copia de seguridad mal guardada, un volcado para depurar— lo robado no serviría para entrar. Y al viajar en cookie HttpOnly, JavaScript no puede leerlo: es la diferencia práctica entre que un XSS robe la sesión y que no pueda.

Superficie expuesta sin autenticación

Por defecto todo endpoint exige autenticación. Lo público se marca uno por uno, que es un olvido visible; al revés el olvido es invisible y deja una puerta abierta. Hoy son anónimos:

EndpointPor quéQué lo protege
/health, /readyEl orquestador los consulta sin credencialesNo exponen datos
Resolver negocio por subdominioEl gateway lo llama antes de que exista sesiónDevuelve solo datos ya públicos. Un negocio eliminado responde igual que uno inexistente, para no convertirlo en un listado de quién estuvo y se fue
Registro y loginQuien entra aún no tiene tokenLímite de peticiones y bloqueo tras 5 intentos

Otras medidas ya puestas

  • Límite de peticiones repartido por cliente cuando lo hay y por IP cuando no. Contar solo por IP castigaría a todo un negocio detrás de una misma oficina; contar solo por cliente dejaría sin freno el tráfico anónimo, que es justo el que conviene frenar.
  • Bloqueo temporal tras cinco intentos fallidos, quince minutos. Temporal y no permanente a propósito: un bloqueo que solo levanta un administrador convierte un ataque contra una cuenta en una forma fácil de dejar a alguien fuera para siempre.
  • Los errores inesperados no salen al cliente. Un error de Postgres sin filtrar cuenta nombres de tablas y columnas, y a veces datos. Fuera va un código genérico y el identificador de traza; la traza completa va al log.
  • Sin secretos en el repositorio. .env está ignorado desde el primer commit, y el servicio no arranca si falta la clave de firma: preferimos no arrancar a arrancar aceptando cualquier token.
  • Consentimiento con fecha (Ley 1581 de Habeas Data). Sin fecha, el consentimiento no se puede acreditar.
  • Contenedores con usuario sin privilegios, nunca root.

9. Lo que NO está verificado

Esta sección es la más importante del documento. Todo lo anterior describe lo que el código dice que hace; aquí está lo que todavía nadie ha comprobado que haga.

Nada se ha ejecutado contra un PostgreSQL real

En la máquina donde se escribió esto no había Docker. Las migraciones se generan y compilan, pero no se han aplicado nunca a una base de datos. Es perfectamente posible que alguna falle al ejecutarse.

QuéEstadoCómo cerrarlo
Las migraciones se aplican sin error Sin probar docker compose up -d y dotnet ef database update por servicio
Las políticas de aislamiento funcionan Sin probar Test con dos clientes: escribir datos con uno e intentar leerlos con el otro. Es el primer test que hay que escribir.
El bloqueo evita la doble reserva Sin probar Ya hay un test de concurrencia escrito con Testcontainers, marcado para saltarse. Basta con Docker para ejecutarlo
La aplicación se conecta como rol no dueño Configurado Está en docker-compose.yml, pero hay que verificarlo en el entorno real
Los eventos llegan a un bus No implementado Hoy se escriben en el log. Falta el adaptador de RabbitMQ
Lógica de negocio de los 5 servicios hechos 142 tests Verificado. No necesita base de datos

Riesgos abiertos, ordenados por gravedad

  1. Que la aplicación acabe conectándose como dueña de las tablas en producción. Anularía el aislamiento por fila sin que nada lo avisara, y la aplicación funcionaría con normalidad. Es el fallo más grave posible en este diseño y el más silencioso.
  2. Que una política de aislamiento esté mal escrita. Hasta que no se pruebe contra Postgres con dos clientes, no hay garantía de que filtre.
  3. Que un consumidor de eventos no sea idempotente. La entrega es «al menos una vez»: descontaría stock dos veces o mandaría dos correos.
  4. Falta rotación de secretos. La política de 90 días está documentada pero no implementada.

10. Cómo seguir

Antes de escribir una línea más

  1. Levantar la infraestructura y aplicar las migraciones. Arreglar lo que falle.
  2. Escribir el test de aislamiento entre clientes. Dos clientes, datos cruzados, y comprobar que ninguno ve los del otro ni con SQL a mano.
  3. Ejecutar el test de concurrencia de reservas, que ya está escrito.
  4. Revisar con qué usuario se conecta cada servicio en cada entorno.

Después

  1. Implementar los cinco servicios que faltan siguiendo docs/pendiente.md, que ya recoge las trampas de cada uno.
  2. Escribir el adaptador real del bus de eventos.
  3. Montar el CI: compilación y tests obligatorios antes de fusionar.
  4. Proteger la rama principal: sin empuje directo, con revisión.

Arranque local

cp .env.example .env          # rellenar los valores
docker compose up -d          # Postgres (10 bases) + RabbitMQ

dotnet build HubNegocios.sln  # 0 errores, 0 avisos
dotnet test  HubNegocios.sln  # 142 tests
